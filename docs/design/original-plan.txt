RESTAURANT MANAGEMENT DASHBOARD + AGENT CONTROL PLANE
=======================================================

CONTEXT
-------
restaurantmanagement/ is a brand-new, empty project directory. The goal is a
restaurant management dashboard built around a HIERARCHICAL AGENT TEAM: one
BOSS agent that the operator releases, which in turn delegates to five
specialized SUBAGENTS, each owning one restaurant-operations domain:

  1. Inventory            -- stock levels, reorder flagging
  2. Supply Chain          -- suppliers, purchase orders, delivery tracking
  3. Employee Management    -- staff, shifts, scheduling gaps
  4. Profit                -- revenue, cost, margin, P&L reporting
  5. Marketing / Product     -- top/slow sellers, promotions, menu proposals

The operator "releases" the Boss with a high-level objective (e.g. "give me
this morning's ops briefing" or "prep for the weekend rush"); the Boss
decides which of the five subagents to delegate to, each subagent runs its
own scoped tool-calling loop against the restaurant's data, and the Boss
synthesizes their results into one summary -- all visible live in the
dashboard as a run tree (Boss run -> child subagent runs). Subagents can
also be released individually for direct testing/debugging, bypassing the
Boss.

Key assumption (flag if wrong): "agents" here means LLM-driven automations
(via the Anthropic SDK), not human staff/shift scheduling.

Other working assumptions for the MVP: single-operator dashboard (no
multi-tenant chains, no public customer ordering UI); no real supplier/POS
integrations yet -- an agent that would take a real-world action (like
ordering more stock) instead writes a proposed action to the DB behind a
human-approval gate; single-process deployment (no Kubernetes/Celery/Redis)
with an explicit upgrade path noted, not built now.

STACK
-----
- Backend: Python 3.12, FastAPI, async SQLAlchemy 2.0 + Alembic, SQLite
  (dev, swappable to Postgres later), anthropic Python SDK. This mirrors the
  proven house convention in chineseappdemo/backend (anthropic==0.121.0,
  fastapi==0.141.1, SQLAlchemy==2.0.51, alembic==1.19.0), so there's no new
  pattern to invent for CRUD.
- Agent execution: no new infra for MVP -- an in-process asyncio.Task per
  run (AgentRunner), APScheduler with SQLAlchemyJobStore for cron-scheduled
  agents (persists across restarts), and a FastAPI WebSocket route per run
  backed by a tiny in-process pub/sub for live log streaming. Each agent
  type is a system prompt + a scoped list of @beta_tool-decorated Python
  functions, driven via client.beta.messages.tool_runner(...) -- no
  hand-rolled agent loop. Upgrade path (not built now): swap the in-process
  queue for Redis/Celery and pub/sub for Redis/Postgres LISTEN/NOTIFY if
  this needs to survive process restarts mid-run or scale beyond one
  machine.
- Frontend: React + TypeScript + Vite (matches chineseappdemo/frontend),
  TanStack Query for data fetching, Tailwind CSS, a useAgentRunStream(runId)
  WebSocket hook for live agent logs.

DATA MODEL
----------
Restaurant domain (minimal, extensible, not the initial focus):
  menu_items, orders, order_items, inventory_items, staff, plus two tables
  the new subagents need:
    suppliers(id, name, contact_info, lead_time_days)
      -- inventory_items gets a supplier_id FK
    shifts(id, staff_id, date, start_time, end_time, role)

Agent platform:
  agent_definitions(id, key, name, description, role[boss|subagent],
    system_prompt, model, tool_allowlist JSON, schedule_cron NULLABLE,
    enabled, created_at)
    -- role distinguishes the one Boss from the five subagents;
    tool_allowlist scopes exactly which tools that definition may call (a
    subagent only gets its own domain's tools; the Boss only gets its five
    delegate_to_* tools).

  agent_runs(id, agent_definition_id, parent_run_id NULLABLE, depth,
    status[queued|running|waiting_approval|succeeded|failed|cancelled],
    trigger_type[manual|scheduled|delegated], input JSON, output_summary,
    error, tokens_used, started_at, finished_at, created_at)
    -- parent_run_id links a subagent run to the Boss run that delegated to
    it (NULL for a top-level Boss run or a standalone manually-triggered
    subagent run), so the UI can render a run tree.

  agent_events(id, run_id, seq, ts,
    type[log|tool_call|tool_result|status_change|delegation], payload JSON)
    -- a delegation event on the Boss's run records which subagent was
    invoked and links to the child run_id, so the Boss's live log shows
    "-> delegated to Supply Chain Agent" inline.

  agent_actions(id, run_id, agent_definition_id, action_type, payload JSON,
    status[pending|approved|rejected], created_at, decided_at)
    -- the single human-in-the-loop approval queue used by every subagent
    that can propose a real-world action (Inventory's reorder proposals,
    Supply Chain's draft purchase orders, Employee Management's
    shift-change proposals, Marketing's menu-change proposals). The Profit
    agent is read-only and never writes here.

Cron schedules live in APScheduler's own jobstore table, keyed by
agent_definitions.id -- either the Boss (e.g. "run a full briefing every
morning at 7am") or an individual subagent can be scheduled.

HOW AGENTS DO WORK
-------------------
Each AgentDefinition maps (via registry.py) to a system prompt + a list of
plain @beta_tool async functions that call the SAME SQLAlchemy CRUD layer
the REST API uses -- no duplicate data access:

  # app/agents/tools/inventory_tools.py
  from anthropic import beta_tool

  @beta_tool
  async def list_low_stock_items() -> str:
      """Return inventory items at or below their reorder threshold."""
      items = await inventory_crud.get_below_threshold(db)
      return json.dumps([...])

runner.py drives execution -- "release" inserts an agent_runs row and does
asyncio.create_task(execute_run(run_id)); "manage" covers listing/filtering
runs (as a tree via parent_run_id), subscribing to /ws/agent-runs/{id} for
live logs, POST /agent-runs/{id}/cancel, approving/rejecting agent_actions,
and editing an AgentDefinition's config/schedule:

  async def execute_run(run_id: UUID) -> str:
      run = await get_run(run_id)
      defn = await get_definition(run.agent_definition_id)
      tools = registry.resolve_tools(defn)   # Boss -> its 5 delegate_to_* tools; subagent -> its domain tools
      runner = client.beta.messages.tool_runner(
          model=defn.model,   # per-agent override; cheap agents can use a lighter model
          max_tokens=16000,
          system=defn.system_prompt,
          tools=tools,
          messages=[{"role": "user", "content": run.input or "Run now."}],
      )
      for message in runner:
          await persist_and_broadcast(run_id, message)  # writes agent_events, pushes to WS
          if await is_cancel_requested(run_id):
              break
      return await finalize_run(run_id, runner)   # returns output_summary

DELEGATION (the Boss -> subagent link) lives in orchestrator.py, which
builds one @beta_tool per subagent and hands them to the Boss's
tool_runner call as its tools:

  # app/agents/orchestrator.py
  def make_delegate_tool(subagent_key: str, boss_run_id: UUID):
      @beta_tool(name=f"delegate_to_{subagent_key}")
      async def delegate(task: str) -> str:
          """Delegate a task to the <subagent_key> subagent and return its result."""
          subagent_defn = await get_definition_by_key(subagent_key)
          child_run = await create_run(
              subagent_defn.id, parent_run_id=boss_run_id,
              trigger_type="delegated", input=task,
          )
          await emit_event(boss_run_id, type="delegation", payload={"child_run_id": child_run.id, "agent": subagent_key})
          return await execute_run(child_run.id)   # recursive call; awaited synchronously so the Boss sees the result
      return delegate

Because execute_run is awaited (not fired-and-forgotten) inside the
delegate tool, the Boss's own tool_runner loop naturally blocks until the
subagent finishes and gets its output_summary back as the tool result --
while the subagent's own events still stream live over its own run_id
WebSocket channel, so the UI can show both the Boss's high-level narration
and each subagent's detailed log simultaneously.

Human-in-the-loop approval (Inventory, Supply Chain, Employee Management,
Marketing) is a tool that writes a "pending" row to agent_actions and
returns a tool_result telling Claude the action is queued for operator
approval; that subagent's run then sits in waiting_approval until the
operator approves/rejects in the Approvals Inbox. A waiting_approval child
run bubbles up as a visible flag on the Boss's run too, so the operator
doesn't have to dig into the tree to find it.

VERIFICATION (PHASE 1 "DONE")
-------------------------------
Operator opens the dashboard, sees the Boss agent and its 5 subagents,
clicks Release Boss with an objective like "give me this morning's ops
briefing," and watches: the Boss run go queued -> running, live-streamed
delegation events as it calls into 2-3 subagents (e.g. Profit for
yesterday's numbers, Inventory for stock issues, Marketing for a promo
idea), each shown as a nested child run in the run tree with its own live
log (including real tool calls reading orders/inventory_items/etc from the
DB), the Boss's run finishing succeeded with a synthesized summary
referencing the subagents' findings. Triggering Supply Chain or Employee
Management directly proposes an action that lands in the Approvals Inbox
and blocks in waiting_approval until approved/rejected. A scheduled Boss
run fires on its own via APScheduler without manual triggering.
